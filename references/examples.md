## 例子 1：否决 — token 中转站

**输入点子**：做一个服务，聚合多家 AI 模型 API，按低于官方的价格转卖。

**流程**：

### 第一关：红线

- **法律风险**：concern
  - 证据：OpenAI 使用条款（2025-09 版本核实）明确禁止未授权转售；多家 API 提供商 ToS 含"不得再分发"条款
  - 来源：https://openai.com/policies/row-terms-of-use/（核实日期 2025-09-XX）
  - 状态：concern → **否决 @ 红线: 法律风险**

第二到第五关：不跑。

### 结论

否决。

### 理由

利润来源是未经授权的转售 + 隐性降级（用便宜模型冒充贵的）。监管与平台双向打击只是时间问题。

## 例子 2：通过 — 小型口腔诊所的 SaaS

**输入点子**：为独立口腔诊所做 SaaS：病历、预约、收费。现有方案（Dentrix、Eaglesoft）$500+/月，对独立诊所过重。

### 第一关：红线

| 类别 | 状态 | 证据 |
|------|------|------|
| 法律风险 | clear | 不涉及盗版、爬虫、刷量 |
| 道德底线 | clear | 医疗服务辅助工具，正向用途 |
| 合规资质 | partial | 病历涉及个人健康信息，需符合《个人信息保护法》《医疗机构病历管理规定》；不直接做诊断，不踩医疗资质 |
| 技术不可控 | clear | 不把 AI 放进诊断决策 |

合规 partial 的处理：在架构层声明"不接触诊疗建议"，病历数据本地存储或受控加密，避免越界。证据来源：《个人信息保护法》（核实日期 2026-XX-XX）。

### 第二关：定位

桶：可商业化变现（来源：用户回答"长期想拿这个吃饭"）

权重：

- 技术深度：中
- 商业回报：高
- 成本容忍度：中

### 第三关：价值

| 问题 | 结论 | 证据 |
|------|------|------|
| 真实问题？ | 是 | 访谈 5 家诊所（2026-XX-XX），全部抱怨 Dentrix 太贵、太复杂；4 家考虑换工具 |
| 现有方案够好？ | 是 | G2 上 Dentrix 差评聚焦"价格 + 学习曲线"；与 2 家诊所现有工作流对比，缺失移动端排班 |
| 人群够大？ | 是 | 国家卫健委 2024 年统计：口腔诊所总数 XX 万家，独立诊所约 XX 万。5% 付费转化即 X 千家 |

蓝海 vs 死海：死海排除——差评、痛点访谈、竞品差评均指向真需求（核实日期 2026-XX-XX）。

### 第四关：难度 × 成本

**难度**：

- 病历 CRUD：能从零写（web 主流栈）
- 预约排班：能从零写
- 收费：能接入成熟方案（Stripe / 微信支付 API，核实日期 2026-XX-XX）
- 多端同步：可学（PWA + 现有方案）

成本估算：

| 类别 | 估算 | 依据 |
|------|------|------|
| 服务器 / 基础设施 | ¥500/月 | 阿里云轻量 + RDS + OSS 当前定价（核实日期 2026-XX-XX） |
| 第三方 API | ¥100/月 | 短信验证 + 支付通道（核实日期 2026-XX-XX） |
| 一次性 | ¥500 | 域名 + SSL + 基础设计 |
| 维护 | 10 小时/月 | 历史 web 项目经验 |
| 分发 | ¥2000/季 | 口腔行业展会 + 行业协会渠道 |
| 冷启动跑道 | 12 周 | 0 收入期（用户答可扛 3 个月） |
| 运营 | 15 小时/月 | 用户答可承担 |

未知成本风险：医保对接政策（来源：当地医保局 2026-XX 月通知）可能变化，目前不接医保可规避。

预设边界：

- v1 不做：医保对接、移动端原生 app、影像 AI 诊断
- v1 做：病历、预约、收费、报表、基础权限

### 第五关：框架退场

- ROI 门槛：$2k/月 recurring，12 个月内
- 时间窗口：18 个月
- 机会成本：推迟部分 freelance（用户答"可接受"）
- 个人契合度：用户答"对医疗运营有兴趣"

### 结论

通过。

### 理由

5 关全清。痛点访谈与差评证据一致，成本 / 收益算得过来，用户有跑道和兴趣。架构层提前划清"不做诊疗建议"的边界，把合规 partial 控制在可处理范围。

### 下一轮触发

拿到 10 家付费诊所后，重跑第三 / 第四关，用真实使用数据校准价值评估与成本模型。

## 例子 3：待修订 — AI to-do 应用

**输入点子**：做一个用 AI 自动分类与优先排序的 to-do 应用，对标 Todoist / TickTick / Things，靠"更聪明"差异化。

### 第一关：红线

| 类别 | 状态 | 证据 |
|------|------|------|
| 法律风险 | clear | — |
| 道德底线 | clear | — |
| 合规资质 | clear | — |
| 技术不可控 | clear | AI 分类不涉高风险决策 |

### 第二关：定位

桶：纯粹想做点能被人用的东西（来源：用户自述"想学移动端开发，顺便做个产品"）。

### 第三关：价值

| 问题 | 结论 | 证据 |
|------|------|------|
| 真实问题？ | 部分 | 调研 20 个目标用户（2026-XX-XX）：8 人说"to-do 已经够用"，5 人说"想要更智能分类"，7 人未表态。AI 分类的"想要"≠"愿意迁移" |
| 现有方案够好？ | 否 | top 3 都成熟，但功能深度已超过大多数用户需求；增加 AI 分类是边际改进 |
| 人群够大？ | 是 | 全球 to-do 应用市场数十亿用户，但巨头壁垒高 |

蓝海 vs 死海：这是红海（核实日期 2026-XX-XX），多家巨头+精品工作室长期占据，迁移成本高。

### 第四关：难度 × 成本

**难度**：

- 移动端原生：用户强项是 web，移动端学习曲线高（来源：用户答"web 熟、移动端入门"）
- 跨端同步：可学但成本高

**成本**：

- 移动端开发学习成本：3–6 个月（用户估）
- 分发：app store 推广成本远高于 web（来源：Sensor Tower 2025 报告）
- 冷启动：在巨头林立的赛道里更难

**预设边界**：

- 不做：协作、看板、甘特图
- 做：核心 to-do + AI 分类

### 第五关：框架退场

- ROI 门槛：低（个人成就感导向）
- 时间窗口：弹性
- 机会成本：移动端学习期不产生用户
- 个人契合度：用户答"想学移动端，附带给别人用"

### 结论

待修订。

### 理由

作为"做给别人的产品"过不了第三关：现有方案已经够好，AI 分类是边际改进，赛道太红。作为"个人学习项目 + 自用工具"则合理——重定位到"纯粹想做点能被人用的东西"，明确 N = 自己 + 几个朋友，重置成功指标。

### 重塑建议

把定位调整为"学移动端开发的练习项目 + 个人工具"，第三关的价值问题就不再卡。第三、第四关可清，结论转 通过（个人版）。

## 常见模式

跑流程时反复出现的：

- **"就是 X 加 AI"** — 通常过不了第三关，除非 X 有明确的"贵 / 复杂 / 慢 / 缺关键功能"。AI 是功能，不是价值主张。
- **"没人做"** — 几乎总是死海，除非能找到目标用户在论坛上的抱怨。
- **"给 [巨大市场] 做的工具"** — 大众市场对独立开发者不是优势。痛点高的小众才是。
- **"商业模式以后再想"** — 在商业桶里是红旗。商业模式决定每个功能决策。
- **"技术有意思"** — 技术影响力桶可以，商业桶致命。定位错位是这套框架里失败最多的原因。
